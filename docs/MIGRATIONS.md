# Database Migrations

T.A.R. uses Alembic for release-to-release schema changes beginning with the release-candidate baseline.

## Fresh installation

Set `TAR_DATABASE_URL`, then run:

```bash
alembic upgrade head
```

Docker Compose runs the migration service automatically before API and workers start.

## Existing pre-Alembic installation

1. Stop writers/workers.
2. Back up PostgreSQL and artifact storage.
3. Upgrade the application code.
4. Verify the existing schema includes the release-candidate workspace columns.
5. Mark the existing schema as the baseline:

```bash
alembic stamp 0001_release_candidate_baseline
```

6. Run `alembic upgrade head`.
7. Start API/workers and run the smoke test.

Do not stamp an unknown or partially upgraded database merely to suppress migration errors.

## Creating a migration

After changing SQLAlchemy models:

```bash
alembic revision --autogenerate -m "describe change"
alembic upgrade head
pytest -q
```

Review autogenerated migrations before committing. Schema migrations should be backward-aware when a rolling deployment could temporarily run mixed application versions.

## Destructive changes

Destructive migrations require an explicit backup/restore plan and should normally be split into expand/migrate/contract phases. Never use a downgrade path that silently deletes user knowledge or artifacts.
